# 项目性能检查与优化

本轮在 `ae88551` 的总览优化基础上，检查数据库、Agent、权限、网络调用、历史数据和前端绘图。评估目标是消除有明确增长趋势的开销、控制资源占用、保持业务及权限正确性。没有引入跨请求权限缓存，没有降低密码哈希强度或关闭 TLS 验证。

## 测量依据

规模测试使用临时数据库，新增5万张订单、3万条约1KB的审计记录、10万条执行事件。原演示业务数据未用于压测写入。每场景3次，下面为中位数；原始样本在 [项目性能优化测量数据.json](项目性能优化测量数据.json)。

| 场景 | 修复前 | 修复后 | 变化原因 |
| --- | ---: | ---: | --- |
| 只查3条产品的权限查询 | 409.37 ms | 3.04 ms | 复制记录从80086条减至3条 |
| 在10万条事件中读取一个任务的201条记录 | 10.56 ms | 3.27 ms | 从按全局ID扫描变为 `(run_id,id)` 索引查找 |
| 500行数据生成100×100热力图选项 | 61.27 ms | 1.96 ms | 从每格重复扫描全部行变为一次Map聚合 |

前端计时是 JSDOM 环境下的图表选项计算，不包含浏览器布局、Canvas绘制或网络时间。500×500的维度组合原先触发 `Maximum call stack size exceeded`；现在在创建矩阵前明确提示先筛选或合并分组。

## 已修复的问题

1. **任意SQL都复制岗位全部数据。** 先用 SQLite `EXPLAIN` 在授权空结构上编译，收集实际引用表，再复制这些表的授权行/列。采用数据库编译器而非字符串替换，支持JOIN、子查询、UNION、CTE和 `main.orders`；保留可见列对应的有效索引。编译和执行使用同一只读授权规则，原库在一次读事务内提供一致快照。`COUNT(*)` 和递归CTE的特殊authorizer行为有专门测试，内部表及元数据仍不可读。
2. **关联查询与历史读取缺索引。** 为客户订单、订单工单、设备状态、工单报工、订单发货建立索引；为会话消息、角色消息边界、任务状态、执行事件、账号私有报表/会话、登录限流和会话撤销建立复合或过滤索引。迁移幂等，保留数据。WAL模式只在数据库初始化时设置，连接热路径不再反复设置持久化模式。
3. **同步数据库I/O阻塞异步服务。** 登录解析、聊天任务创建、Agent历史读取/事件/消息持久化、状态更新、报表验证与保存均在工作线程执行，数据库连接在对应线程内创建和释放。ContextVar登录身份随线程任务传递；每个请求和工具仍重新验证会话。
4. **密码计算持有全库写锁。** scrypt验证和重置密码的哈希计算移至写事务外；进入事务后再次检查凭据版本、启用状态与限流计数，防止并发改密时使用过期凭据登录。事务仅覆盖必要的状态更新。
5. **每轮模型调用重建连接。** DeepSeek异步客户端随服务生命周期创建、释放，复用连接池；每次调用重新构造本岗位工具，不共享用户授权。JSON请求构造移至工作线程，超过250000字符的模型请求在发送前拒绝。模型等待受本轮剩余8分钟预算限制。
6. **Agent任务没有准入上限。** 默认全局4个、单账号2个运行任务，在同一个数据库写事务里检查和创建，避免并发超卖；超限返回429与 `Retry-After: 5`，不创建空会话/消息/任务。通过 `MAX_AGENT_RUNS/MAX_USER_RUNS` 配置。没有建立无界等待队列。
7. **历史消息和事件一次全部返回。** 使用ID游标，每页最多200条及约2MB内容；单条大记录可单独成页以确保游标推进。前端提供加载更早消息入口，处理事件 `has_more` 后再判断任务完成。跨分页的报表工具结果附带后端解析的工具名，避免图表因工具调用位于上一页而消失。最近任务列表只读取20条。
8. **单个查询结果/报表/上下文没有字节预算。** SQL逐行读取，保留500行上限并增加约2MB行结果预算、1MB SQLite记录限制和200列限制，不先获取全部结果再截断。报表快照限制4MB。历史加载先在SQL中检查大小，再反序列化消息；模型请求也检查本轮新增工具结果。超限不会默默修改数值或编造统计。
9. **前端一次生成过多内容。** 报表编辑器每页50行，编辑与导出仍保留完整草稿；执行日志展开时才序列化详细JSON；聊天图表临近视野时才创建ECharts实例，离开页面时释放待绘图任务和实例；透视表/热力图预聚合，矩阵限制10000格。
10. **会话心跳重复拉取全量启动信息。** 增加轻量 `/api/auth/session`，复用当前请求刚验证的身份，只返回当前CSRF令牌。前台页面每30秒检查，后台页暂停，回到前台立即检查；不再为心跳生成工具JSON Schema或请求ERP健康接口。

# 临时数据库扩容测试，不写演示业务数据库

最终验证：60项后端测试、18项前端测试通过；真实AI业务验收47项、岗位验收16项全部通过。重启实际演示实例后，管理员、销售、生产总览接口中位数分别为23.57、20.76、19.93毫秒。

测试覆盖查询按需加载、授权字段/客户范围、递归查询预算、结果截断、历史和日志分页无丢失/重复、跨分页图表、会话撤销、并发身份隔离、密码计算不持有写锁、鉴权不在事件循环执行、任务容量拒绝无副作用、图表聚合与编辑分页。真实模型验收记录在 [真实模型业务验收轨迹.json](真实模型业务验收轨迹.json) 和 [岗位权限真实模型验收轨迹.json](岗位权限真实模型验收轨迹.json)。

## 仍然保留的架构边界

- 权限查询仍会物化**被引用表中该岗位可见的全部记录**；对同一张百万行表的简单LIMIT查询，复制开销仍随该表规模增长。本轮修复了读取无关表的开销，没有把SQL直接放回未过滤原库执行。大表场景需要继续设计数据库原生权限隔离及查询下推，不能靠取消权限过滤换速度。
- SQLite仍是单机单写者，索引、WAL和缩短事务不等于多写者数据库。大数据量、写密集或多副本部署需要独立的存储与容量方案。
- Agent任务仍运行在服务进程中，重启会标记中断；尚无跨进程持久任务队列、自动接管或分布式调度。并发上限控制本机资源，不提供上述能力。
- 当前检查覆盖有限的本机数据规模与功能并发，没有完成目标生产硬件上的长期压测、P95/P99服务等级或故障注入验收。HTTP入口的完整请求体限额、全站流量控制和部署级监控也不在本轮改动内。

因此这轮提升了实现质量和可预测性，但不把单机Demo宣称为已经完成生产容量验收的系统。
