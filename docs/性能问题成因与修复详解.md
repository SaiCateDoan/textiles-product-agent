# 性能问题是怎样产生的，又是怎样修复的

这份文档解释本项目两轮性能修复的因果关系：原实现做了什么、多出来的时间花在哪里、数据和并发增加后为什么会变慢，以及修复为什么有效。

第一轮由“新增岗位账号后，经营总览加载需要好几秒”触发，对应提交 `ae88551`。第二轮检查了查询、Agent、数据库、历史记录和前端绘图，对应提交 `033f76a`。

文中的简化代码用于说明关键机制，不是完整实现。测量数据来自本机测试；没有计时数据的问题，会说明其风险和验证方式，不把推测当成实测结论。

## 1. 经营总览：很小的查询，为什么会累加到几秒？

### 原来的执行过程

总览需要订单金额、待交付订单、生产中工单、低库存原料、良品率等指标，还需要几张近期业务表。加入岗位权限后，后端会判断当前岗位能看哪些内容，再逐项查询。

问题在于，这些查询是串行执行的。管理员一次总览触发11次内部HTTP请求，销售6次，生产8次；后一个请求要等前一个完成。

每次内部请求又会创建并销毁一个HTTP客户端：

```python
# 原来的关键结构：每调用一次，就创建一次客户端。
async def request(path, body):
    async with httpx.AsyncClient(...) as client:
        return await client.post(path, json=body)

# 总览逐项等待。
for sql in dashboard_queries:
    result = await erp.query(sql)
```

创建客户端不只是创建一个普通Python对象。本机性能分析发现，它会初始化SSL上下文并加载证书；即使这次访问的是本地HTTP地址，默认客户端初始化仍然有这一步。单次证书加载约286毫秒，整个客户端创建通常约300–400毫秒。

管理员总览的总耗时可以近似理解为：

```text
总耗时 ≈ 11 ×（客户端初始化 + 内部请求 + 权限数据准备 + SQL查询）

仅 11 × 300毫秒，就已经是3.3秒。
```

当时身份解析仅约2–3毫秒，权限SQL查询约3–5毫秒。主要时间消耗在重复初始化，而不是这些小查询的计算上。因此，“配置账号后出现变慢”的直接原因是权限版本改变了总览请求方式，不能据此认定账号数量本身导致数据库变慢。

### 修复方式

修复同时减少了“每次调用的固定开销”和“调用次数”：

1. HTTP客户端在Agent服务启动时创建，在服务关闭时释放，中间复用连接池。
2. 总览只调用一次内部 `/dashboard` 接口，由ERP/MES后端集中计算全部可见指标。
3. 一次总览只准备一份当前岗位的权限数据快照，所有指标在同一份快照上读取。

```mermaid
flowchart TB
    subgraph before[修复前：管理员一次总览]
        A[网页请求总览] --> B[Agent逐项查询]
        B --> C[最多11次串行内部请求]
        C --> D[每次新建客户端、准备权限数据、执行查询]
    end
    subgraph after[修复后：同一次总览]
        E[网页请求总览] --> F[使用已启动的HTTP客户端]
        F --> G[一次内部总览请求]
        G --> H[一份权限快照，计算全部可见指标]
    end
```

这里复用的是**客户端和连接**，不是上一个用户的身份或查询结果。用户会话仍逐次放入请求头并重新校验；没有通过关闭证书验证来提速，也没有跨用户共享授权缓存。

第一轮实测，管理员总览由3784毫秒降到约27毫秒。代码入口是 [adapter.py](../app/adapter.py) 的 `ERPAdapter`，以及 [domain.py](../app/domain.py) 的 `dashboard`。

## 2. 权限查询：为什么查3条产品，却复制了8万条数据？

### 原实现有一个明确的安全目的

Agent可以生成只读SQL。为了防止它查询未授权表、字段或客户数据，系统先创建一个临时内存数据库，只放入当前岗位允许看到的内容，再在里面执行SQL。

这让权限隔离比较直接：用户看不到的字段和记录，根本不会出现在查询所使用的数据里。例如生产岗位的订单表没有单价字段，销售岗位的订单表只包含负责客户的订单。

原实现的问题是，无论查询用到了什么表，都会复制该岗位允许读取的**全部表**：

```text
用户请求：SELECT id, name FROM products LIMIT 3

原执行过程：
复制客户、订单、工单、库存、审计等所有授权数据
→ 在这些数据中查询3条产品
→ 丢弃整个临时数据库
```

当演示数据只有几十条时，这个成本不明显。但在独立测试库增加5万张订单、3万条审计记录后，只查3条产品也会复制80086条记录，查询中位耗时达到409.37毫秒。

开销随**岗位全部可见数据的规模**增长，而不是随这次查询真正需要的数据增长。

### 修复：先确定引用了哪些表，再加载这些表

新流程分成两步：

```text
第一步：只建立授权表和字段的空结构
       → 用SQLite EXPLAIN编译SQL
       → 从授权回调收集查询实际引用的表

第二步：只复制这些表的授权记录
       → 执行原SQL
       → 返回结果并释放临时数据库
```

`EXPLAIN`在这里用于编译，不执行用户查询。它可以识别JOIN、子查询、UNION、CTE等结构，比从SQL文本中搜索表名可靠。编译时也启用只读授权规则，所以越权字段或写操作会在加载业务数据前被拒绝。

例如，查询只引用 `products`，就不再复制订单或审计；查询连接了 `orders` 和 `products`，才加载这两张表。源数据在同一个读事务内提取，客户范围和字段过滤仍然先于查询执行。

测试过程中还处理了SQLite授权回调的一个细节：`COUNT(*)`与部分CTE读取可能没有数据库名。不能简单把“没有数据库名”当作安全的临时结果，否则会漏记实际引用表或错误放行内部表。实现区分真实物理表和临时CTE结果，并用测试覆盖这些情况。

同一个规模场景下，修复后只复制3条产品记录，耗时降到3.04毫秒。实现位于 [permissions.py](../app/permissions.py) 的 `projected_db/read_authorizer`，入口位于 [domain.py](../app/domain.py)。

### 这次优化没有解决什么

目前仍会复制“被引用表中当前岗位可见的全部记录”。如果产品表本身有一百万条授权记录，`LIMIT 3`并不会让复制阶段只读取3条。这次消除了**无关表的复制**，尚未实现对任意用户SQL的完整查询下推。

直接让Agent查询未过滤原库虽然可能更快，却会丢失原有权限边界，因此没有采用这种改法。

## 3. 执行日志：有主键，为什么仍然需要额外索引？

原事件表有全局递增的 `id` 主键，而前端的典型读取方式是：

```sql
SELECT *
FROM events
WHERE run_id = ? AND id > ?
ORDER BY id
LIMIT 201;
```

主键可以帮助数据库找到“某个ID之后”的位置，但其中会混有大量其他任务的日志。数据库仍需要沿着全局ID扫描，再筛选当前 `run_id`。返回201条当前任务的事件，可能检查远多于201条记录。

修复增加了复合索引：

```sql
CREATE INDEX events_run_id ON events(run_id, id);
```

可以把这个索引理解为“先按任务整理，再在每个任务里面按ID排序”。数据库先定位当前任务，再读取游标后面的那一段，就不必逐条排除其他任务。

测试查询计划从：

```text
SEARCH events USING INTEGER PRIMARY KEY (rowid>?)
```

变为：

```text
SEARCH events USING INDEX events_run_id (run_id=? AND id>?)
```

在10万条事件的测试库中，同一读取场景由10.56毫秒降到3.27毫秒。

类似地，客户订单、订单工单、工单报工、会话消息、任务状态和账号私有报表等，也根据实际过滤和排序条件补充了索引。索引会占空间并增加写入维护成本，所以采用的是针对已存在查询路径的索引，而不是给每列都加索引。

同时，把WAL模式设置从“每次建立连接”移到数据库初始化阶段。WAL是持久化配置，没有必要在每次请求上重复设置。相关代码在 [database.py](../app/database.py) 和 [auth.py](../app/auth.py)。

## 4. 并发卡顿：为什么用了async，其他请求仍可能被拖住？

### `async def`不会自动把同步操作变成异步

异步服务的事件循环负责调度多个请求。当一个请求等待网络时，它可以让出执行机会，去处理其他请求。

但是，标准库SQLite访问是同步调用。原代码在一些 `async def` 函数中直接连接数据库、启动事务、写入消息或查询历史：

```python
async def handle_request():
    # 这里的数据库调用不会因为外层是async而自动让出执行机会。
    with transaction('agent') as db:
        db.execute(...)
```

数据少、磁盘空闲时，这可能只花几毫秒。但一旦发生锁等待或较慢的磁盘操作，等待会占住事件循环，其他本来无关的请求也不能及时得到调度。页面就可能表现为整体卡顿，而不是只有那个数据库操作慢。

### 修复：把阻塞工作交给工作线程

现在，可能阻塞的鉴权、聊天任务创建、历史读取、Agent日志和消息持久化、报表保存等，通过 `asyncio.to_thread` 执行：

```python
async def handle_request():
    result = await asyncio.to_thread(database_work)
    return result
```

等待数据库的线程仍可能需要排队，但事件循环可以继续处理网络响应和其他请求。数据库连接在对应工作线程内创建并释放，没有把同一个SQLite连接拿到多个线程共用。

登录身份通过上下文变量传递到工作线程，鉴权仍然生效。测试验证了身份解析不在事件循环线程执行，以及并发请求不会混用账号。

这个修改改善的是服务并发时的响应能力，不能据此声称SQLite单条查询本身变成了异步或变快了。相关实现分布在 [server.py](../app/server.py)、[runtime.py](../app/runtime.py)、[adapter.py](../app/adapter.py) 和 [reports.py](../app/reports.py)。

## 5. 登录：为什么一次密码校验可能拖住聊天写入？

密码验证使用scrypt。它本来就需要一定计算量，这有助于提高暴力猜测密码的成本。问题是原实现把这段计算放进了数据库写事务：

```text
取得Agent数据库写锁
→ 查询用户
→ 计算密码哈希
→ 判断密码
→ 写入登录状态
→ 提交并释放写锁
```

SQLite同一个数据库文件同时只有一个写者。在密码计算期间，这个写事务没有修改数据，却一直占用写入位置，聊天消息、事件或其他登录状态更新就可能等待。这里影响的是同一个Agent数据库文件的写入，并非所有数据库都被统一锁住。

修复后的流程是：

```text
读取候选凭据并关闭读连接
→ 在写事务外计算密码哈希
→ 开始短写事务
→ 再检查凭据是否仍相同、账号是否启用、是否触发限流
→ 写入结果并提交
```

再次检查很重要：如果计算密码期间管理员重置了密码或停用了账号，旧凭据就不能继续创建有效登录。重置密码所需的哈希计算也移到了写事务外。

这项修复缩短了写锁的持有范围，没有降低密码哈希强度。测试在密码计算过程中尝试取得另一个写事务，确认此时数据库写锁没有被占用。实现见 [auth.py](../app/auth.py) 的 `login/save_user`。

## 6. Agent：单次对话能运行，为什么多人使用时还需要限制？

### 重复建连会随着工具轮次累加

一次Agent任务可能多次经历“调用模型→执行工具→再次调用模型”。原实现每轮模型请求都新建HTTP客户端，重复初始化连接环境；还无法有效复用上一轮连接。

现在DeepSeek客户端随服务启动和关闭，在整个服务生命周期内复用连接池。每轮仍重新生成当前岗位可用的工具，消息也按本次调用传入，不把用户上下文存进共享客户端。

模型请求JSON构造放到工作线程中；模型等待使用本轮剩余时间预算，避免等待网络时无限超过任务预算。这里没有给出“模型推理快了多少”的结论，因为模型生成时间受服务状态、输入和输出内容影响，不能用本地建连测试替代真实端到端推理测量。

### 没有准入上限，会把有限资源变成无界竞争

如果每收到一个请求就创建任务，用户可以同时启动大量会话。它们会一起占用模型连接、内存、数据库写入机会和API额度；即使每个任务都不大，合计资源也可能超出机器能力。

现在默认允许：

- 全系统最多4个运行中的Agent任务。
- 每个账号最多2个运行中的Agent任务。

检查数量与创建任务放在同一个写事务中。这避免两个并发请求都读到“还剩一个名额”，随后同时插入任务的竞争问题。超限返回429和重试提示，不留下空会话、空消息或空任务，也不建立无限等待队列。

### 限制行数不等于限制内存和模型输入

原先已经有查询500行的上限，但500个很大的文本字段仍然可能占用大量内存。并且，如果先把结果全部取出，再截断返回，内存开销已经发生。

现在逐行读取并计入预算，主要边界包括：

| 对象 | 当前限制及处理 |
| --- | --- |
| SQL行结果 | 最多500行、约2MB；超出后停止读取并标记截断 |
| SQLite记录与列 | 单条记录上限1MB，输出列上限200 |
| 报表快照 | 超过4MB拒绝保存，并提示缩小范围或先聚合 |
| 历史上下文 | 在反序列化整段历史前，先检查存储内容大小 |
| 模型请求 | 序列化后超过250000字符，在发送前拒绝 |

字符预算不等于精确的模型token数量。这些限制用于控制本机资源和请求规模，不能代替具体模型的上下文容量校验。遇到大范围统计，应让SQL先聚合，而不是把全部明细送给模型再计算。

代码入口为 [runtime.py](../app/runtime.py)、[server.py](../app/server.py)、[config.py](../app/config.py)。

## 7. 历史记录：为什么必须连API、前端和图表一起改？

原接口会一次返回某个会话的全部消息、某个任务的全部事件。随着历史增长，数据库读取、JSON解析、网络传输和页面节点创建都会增长。即使补了索引，传输和渲染所有内容的成本也不会消失。

修复使用ID游标分页：

```text
会话：读取最近一页 → 点击“加载更早的消息” → 读取最早ID之前的一页
日志：读取上次事件ID之后的一页 → 若has_more=true，继续读取下一页
```

每页最多200条，并有约2MB内容预算；单条较大的已有记录允许单独成页，以免游标永远无法向前推进。分页避免了每次都从第一页开始跳过大量记录，也避免首次打开页面时加载整个历史。

实现中必须处理两个容易遗漏的正确性问题：

**任务完成不等于日志已经取完。** 任务状态可能已是 `completed`，但当前响应只包含前200条事件。前端与验收脚本需要先处理完 `has_more`，才能结束读取，否则可能丢失后面的业务结果或图表。

**工具调用和工具结果可能分处两页。** 图表来自成功的 `create_report` 工具结果。如果当前页只有结果、上一页才有调用声明，前端原来的匹配方式会认不出图表。现在后端在验证会话所有权后，补充结果对应的工具名称，前端据此恢复报表；并不需要为了一张图表加载全部历史。

相关实现见 [server.py](../app/server.py) 的 `session/run`、[database.py](../app/database.py) 的 `payload_page`，以及 [frontend/app.js](../frontend/app.js) 和 [renderers.js](../frontend/renderers.js)。

## 8. 图表：只有500行数据，为什么仍可能卡顿？

### 原聚合算法重复做了大量相同工作

透视表和热力图需要按“X维度×分组维度”形成交叉矩阵。原实现计算每一个格子时，都会重新扫描全部数据：

```javascript
// 原来的关键计算方式。
const sum = (x, group) => rows
  .filter(row => row.x === x && row.group === group)
  .reduce((total, row) => total + row.value, 0);
```

设原始行数为N、X类别数为X、分组类别数为G，计算量大致是 `N × X × G`。500行、100个X类别、100个分组，就需要约500万次行匹配。

新实现先扫描一次，把同一维度组合的值累加到Map，再从Map读取各个格子的结果。计算量变为约 `N + X × G`：上述例子中，一次500行聚合加一万个格子的读取，就能得到同样结果。

在JSDOM中的图表选项生成测试，从61.27毫秒降到1.96毫秒。这个数字只衡量聚合和选项构造，不包含真实浏览器绘图时间。

此外，500行数据仍可能各自产生不同的X类别和分组，形成500×500，也就是25万个格子。原实现曾在选项生成阶段触发 `Maximum call stack size exceeded`。现在在创建矩阵前检查组合规模，超过一万格就提示先筛选或合并分组，避免继续制造难以阅读的大矩阵。

### 页面不应提前生成所有细节

算法优化之外，还减少了不必要的首次渲染工作：

| 原来的行为 | 新的行为 | 为什么有效 |
| --- | --- | --- |
| 编辑器一次生成全部行的输入框 | 每页生成50行 | 限制同时存在的输入控件数量，完整草稿仍用于保存和导出 |
| 日志折叠时也生成完整JSON文本 | 展开时才序列化详情 | 用户没有查看的详情不消耗这部分格式化与DOM开销 |
| 打开聊天就创建全部图表实例 | 图表临近视野时再创建 | 历史图表较多时，先处理用户实际看到的部分 |
| 离开页面可能仍有待绘图任务 | 释放观察器中的待处理节点和图表实例 | 避免保留已离开页面的节点和对象 |

测试还验证了编辑器翻页后修改的是原始草稿中的正确行，而不是把第二页第一行误写到第一行。实现位于 [frontend/app.js](../frontend/app.js) 与 [renderers.js](../frontend/renderers.js)。

## 9. 心跳：每30秒的小请求，为什么也值得检查？

原页面为了确认登录是否有效，每30秒调用完整的 `/api/bootstrap`。这个接口除了检查登录，还会生成工具参数结构并向ERP请求健康状态。这些启动信息并不是每次会话检查都需要的。

新加的 `/api/auth/session` 只使用中间件刚刚验证的身份，返回当前会话所需令牌，不再重新生成全部工具定义或访问ERP。后台标签页暂停周期检查，回到前台时立即验证。

这项改动减少了“在线用户数×打开标签页数×运行时间”累积出来的重复工作，没有取消会话撤销检查，也没有把登录有效性长期缓存起来。

## 10. 怎么确认是有效修复，而不是只把数字变小？

验证分为三类：

**性能测量。** 对修复前后使用相同场景，每项采集3次并取中位数。规模测试在临时数据库中执行，未向当前演示业务库写入压测数据。

| 场景 | 修复前 | 修复后 | 测量范围 |
| --- | ---: | ---: | --- |
| 管理员经营总览，第一轮修复 | 3784.27 ms | 26.96 ms | 本机HTTP接口，不含页面绘制 |
| 扩容数据中查询3条产品 | 409.37 ms | 3.04 ms | 权限数据准备与SQL执行 |
| 10万事件中读取201条任务事件 | 10.56 ms | 3.27 ms | 数据库查询，不等于完整网页耗时 |
| 一万格热力图选项生成 | 61.27 ms | 1.96 ms | JSDOM计算，不含Canvas绘图 |

第一行来自第一轮测量，后三行来自第二轮规模检查，不应把不同场景的耗时直接互相比较。它们也不是生产环境的P95/P99或长期负载指标。

**自动化正确性测试。** 最终60项后端测试、18项前端测试通过，覆盖权限范围、隐藏字段、查询预算、索引相关路径、分页完整性、跨页图表、并发身份隔离、密码计算不持写锁、任务准入和前端聚合等。

**真实AI业务验证。** 通过真实DeepSeek完成采购、排产、报工、发货、补产、技能和图表流程，并验证不同岗位权限。业务验收47项、岗位验收16项全部通过。这用于确认优化没有破坏完整调用链，而非证明模型推理延迟固定不变。

## 11. 这些修复离“生产最优”还有什么距离？

这轮解决的是已经定位的浪费和资源失控点。当前系统仍有明确边界：

- 查询某张大表时，仍要复制这张表中该岗位可见的全部记录；任意SQL的安全查询下推尚未实现。
- SQLite仍是单机单写者，索引和短事务不会把它变成多写者数据库。
- Agent任务仍在服务进程内执行，重启会标记中断，尚不支持跨进程持久队列、自动接管或分布式调度。
- 还没有基于目标生产硬件、真实业务规模和持续流量完成容量、尾延迟及故障恢复验收。

后续如果继续演进，应根据真实的慢查询、数据规模、写入频率和任务并发决定下一步架构，而不是仅凭“生产级”三个字增加缓存、线程或服务。当前保留了可复现的测量脚本和边界测试，后续优化可以继续用同样方式核验收益与正确性。
