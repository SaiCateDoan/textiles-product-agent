# 纺织工厂 Agent 的痛点与解法

日期：2026 年 11 月 3 日。本文把产品讨论中的问题转化为设计决策和可验证结果。所有“验收”均为待执行要求，不代表已经通过。

## 1 痛点与方案对照

| 编号 | 痛点 | 解法 | 剩余限制 | 验收方法 |
| --- | --- | --- | --- | --- |
| P01 | 用户问题超出预设工作流就无法回答 | Deep Agents 主体自主规划、查询和迭代；工作流仅作为业务工具 | 模型仍受数据、工具和预算限制 | 用开发者未预写逻辑的问题测试，不添加专用报表工具也能完成分析 |
| P02 | 每新增一种报表都要开发一个函数 | 提供数据发现、组合查询、Python/SQL 沙箱和产物能力 | 复杂统计需要验证方法和假设 | 用户临时改变分组、指标或比较条件，Agent 修改代码完成 |
| P03 | 有 Java API，却无法高效跨模块分析 | 业务 API 与分析数据通道分开；先批量导出，后建分析层 | 历史快照与实时性取决于源系统 | 跨销售、生产、质量和回款分析不造成生产接口无界扫描 |
| P04 | 模型不认识字段，连接后重复统计 | 目录提供粒度、关系、单位、状态和样本；代码验证连接基数与总计 | 某些口径需要业务人员确认 | 故意制造一对多连接，Agent 发现重复计数并修正 |
| P05 | 垂直领域知识写死后限制探索 | 纺织 Skills、公式和查询示例作为按需经验；允许临时指标 | 新口径不能自动变为公司标准 | 没有对应 Skill 的新问题仍能研究，临时指标明确披露 |
| P06 | 电商数据依赖用户登录，纯云端难以接入 | SaaS 主 Agent 调用本地扩展或执行器，复用授权浏览器会话 | 验证码、平台限制和账号失效仍存在 | 手动登录后完成目标采集，Cookie 不进入云端日志和数据集 |
| P07 | 为本地采集被迫维护两套完整 Agent | 一个主 Harness，多执行环境；仅必要时启用受限浏览器子 Agent | 离线本地自主运行需另行设计 | 同一会话混合查询 ERP、采集浏览器和云端分析，任务可追踪 |
| P08 | 强行统一两端工具导致错误路由 | 统一契约与结果，保留执行前提、设备与账号绑定 | 两端不能在所有功能上互换 | 设备离线时返回等待状态，不偷偷换账号或改为云端抓取 |
| P09 | 工具列表和系统提示频繁变化，前缀缓存损失 | 稳定核心与版本、追加动态状态、按需 SDK 文档、兼容时延迟加载 | 缓存受服务商、过期及压缩影响 | 对比设备上线前后请求前缀；记录命中 token、总费用和延迟 |
| P10 | 海量 API 说明和中间结果占满上下文 | 工具发现、代码组合调用、文件外置、摘要与证据索引 | 外置后必须保证可找回且权限不变 | 十万行数据不进入模型消息，Agent 仍可追查异常样本 |
| P11 | 文件 Backend 被误认为安全沙箱 | 区分文件存储与代码隔离，部署独立执行环境 | 需要维护网络、依赖、配额和补丁 | 沙箱代码无法访问宿主凭据、其他租户文件或未授权网络 |
| P12 | Agent 编码可绕过工具权限 | 数据代理、短期权限、网络出口约束；所有访问路径统一鉴权 | 已读数据的撤权需要处理派生文件 | 用代码、子任务和本地路径尝试越权，均被执行层拒绝 |
| P13 | 页面或文档内容诱导 Agent 执行业务操作 | 外部内容按数据处理，工具和数据权限硬约束，写入独立校验 | 提示注入不能仅靠过滤彻底解决 | 恶意商品描述不能触发 ERP 写入、外传数据或修改可信 Skills |
| P14 | 超时、重试或恢复造成重复建单 | ERP 端幂等、操作账本、结果查询、版本检查 | 外部系统不支持幂等时只能降低自动化程度 | ERP 已成功但响应丢失后恢复，最终只存在一张单据 |
| P15 | 设备休眠、浏览器退出导致任务丢失 | 持久任务协议、租约、事件序号、断点和状态核对 | 用户设备不能提供天然全天在线服务 | 采集到一半断网，恢复后已完成记录不丢、不重复计入分析 |
| P16 | 插件越多，语义与版本越来越不一致 | 数据目录、语义、SDK、命令与 Skills 一起版本化 | 无法消除所有厂商差异 | 第二个 ERP 使用相同研究任务，特殊提交语义仍明确展示 |
| P17 | 竞品能抓到，但价格和规格不可比 | 保存 SKU、规格、单位、优惠条件、时间与证据，分层判断可比性 | 页面缺字段时只能降低置信度或排除 | 样品价、不同幅宽和缺失克重不被混成同一商品比较 |
| P18 | 长任务压缩后丢失目标或证据 | 目标、笔记、代码、数据和证据外置；压缩只改变活动上下文 | 摘要可能遗漏细节，需要检索恢复 | 强制压缩并重启后，继续完成原目标且关键结论可回溯 |
| P19 | 为“智能”过度拆分多 Agent，成本和错误上升 | 默认单主 Agent，独立子任务按需启用，限制权限和预算 | 某些并行任务仍需合并与冲突处理 | 对比单 Agent 基线，仅在效果或延迟改善时保留子任务 |
| P20 | 每一步都审批，用户无法连续工作 | 继承已有授权，读分析自动运行，业务写入按角色和风险规则审批 | 需要明确企业授权边界 | 普通研究不中断；审批绑定参数，修改后不能沿用旧批准 |
| P21 | 图表漂亮但结论错误或无法复算 | 保存快照、SQL、代码、指标定义、证据和产物清单 | 原始数据不完整时无法制造确定性 | 抽查结论能由同一数据快照重算，相关关系不冒充因果 |
| P22 | 会话和报告分享泄露派生数据 | 元数据、样本、文件、记忆、日志和报告均执行权限继承 | 撤权不能收回用户此前合法下载的副本 | 无源数据访问权的用户不能借助报告链接读取敏感内容 |

## 2 开放式分析与业务可靠性的平衡

对应 P01、P02、P05、P14、P20。

自主性应放在研究路径和计算方法上。Agent 可以改变假设、追加查询、重新编写图表，甚至组合此前没有一起使用过的数据源。审批、过账和付款等动作仍由业务服务决定是否可执行。

对于同一个需求，前半段“找到需要补货的原因并比较方案”可以完全自主；后半段“提交采购单”遵守企业权限。不要把自主研究塞进固定流程，也不要为了自由探索取消业务写入契约。

验收必须包含没有标准模板的新问题，并记录 Agent 是否真的查询、执行代码和检查结果。仅看最终回答语言流畅度不足以评价系统。

## 3 云端与本地工具差异

对应 P06、P07、P08、P15。

需要同步的是任务目标、授权范围、进度、结果和证据引用。无需同步 Cookie、完整浏览器配置、全部聊天历史和模型 KV 缓存。

保留两个执行入口：云端分析沙箱负责可隔离的计算，本地浏览器桥接负责用户登录环境。文件路径、账号、登录状态和可访问网络都不同，执行器必须明确说明结果来自哪个环境。

即使底层支持同名工具，也只有语义、数据范围和前提一致时才允许自动路由。用户设备离线时，任务可以等待或交付部分结果；不得无提示更换执行身份。

## 4 前缀缓存与动态能力

对应 P09、P10、P18。

稳定前缀与自主探索并不矛盾：用稳定的文件、查询、执行和发现工具，按需读取业务文档；动态研究结果追加到会话尾部。必要时使用供应商支持的尾部工具加载，而不是每轮重建整个工具列表。

Deep Agents 会根据 Backend 能力处理执行工具，因此“设备离线就换 Backend”可能引入工具定义变化。采用固定的分析 Backend 类型和单独的浏览器桥接工具，断线作为工具状态呈现。以实际发送的模型请求验证，不能只凭框架配置推断缓存命中。[Deep Agents 沙箱文档](https://docs.langchain.com/oss/python/deepagents/sandboxes)

上下文压缩、权限撤销和模型切换可能必须改变前缀。允许这些变化，以成功任务的总成本和质量衡量优化，不追求脱离业务的最高命中率。

## 5 数据权限与生成代码

对应 P03、P04、P11、P12、P13、P22。

“权限内自由分析”需要两层实现：数据服务确定可读对象和字段；代码沙箱允许用户对这些数据开展广泛计算。Agent 不能通过 Python 的 HTTP 客户端绕过数据服务，因此必须同时控制身份和网络出口。

查询合法不代表结论正确。语义目录和校验程序还要解决一对多连接、时间口径、单位和重复计数。一个只读数据库账号也不等于完成了租户隔离；实际数据库角色、策略和查询路径都要验证。

派生报告、文件和记忆继承访问范围。对于敏感数据，默认不将原始样本写入模型追踪平台；调试使用脱敏数据或经授权的短期诊断流程。

## 6 不能靠架构消除的问题

- 源系统从未保存的数据不能通过模型补出。例如缺少历史库存快照时，不能保证还原某日真实可用库存。
- 本地登录浏览器不能保证平台允许持续自动访问，也不能保证账号永不触发验证。
- 新增 ERP 插件仍需要业务语义映射和兼容性测试，OpenAPI 自动生成只能降低机械工作量。
- Agent 有代码执行能力不意味着统计方法自然正确，需要计算校验、业务评测和必要人工复核。
- 模型、框架和供应商更新可能改变工具行为与缓存表现，必须按版本回归。

这些限制应以缺失数据、任务状态和证据边界呈现给用户，不应被隐藏成看似完整的分析结论。
